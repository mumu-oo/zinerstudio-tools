# 擺攤 POS 技術方向 v1

## 這份文件是做什麼的

這份文件不是工程實作細節，也不是程式碼規格。

它的用途是用白話方式說清楚：

- 這個 POS App 之後要做成什麼
- 為什麼現在先用 HTML prototype
- 真正做成 iPad / Android App 時，技術方向怎麼選
- 資料要放哪裡
- 第一版先做什麼、不做什麼

這份文件的目標是讓非工程背景的人也能看懂。

---

## 目前產品方向已定案的事

這個產品不是網站，也不是桌機工具。

目標一直都是：

- 給平板使用的 POS App
- 適用於同人展、市集、創作者擺攤
- 離線可用
- 中文介面優先
- 前台重視快速找商品與結帳
- 後台重視商品、庫存、預購與付款方式管理

目前只是先用 HTML 做 prototype，目的是確認：

- 視覺設計
- 操作流程
- 前後台頁面結構
- 功能有沒有漏掉

所以現在的 HTML 不是最終產品形式，而是正式 App 的設計藍本。

---

## 為什麼現在先做 HTML prototype

因為這個階段最重要的不是先寫資料庫，而是先確認：

- 畫面長什麼樣
- 用起來順不順
- 哪些功能真的需要
- 哪些功能只是想像中需要

如果沒有先做 prototype，就直接寫正式 App，後面通常會一直改：

- UI 改掉
- 頁面流程改掉
- 欄位改掉
- 功能優先順序改掉

這樣正式開發的成本會更高。

所以目前的流程是正確的：

1. 先做 prototype
2. 確認設計與流程
3. 再做技術選型
4. 最後才進正式開發

---

## 這個 App 真正做出來後會是什麼

最終形式應該是：

- iPad 可用的 App
- Android 平板可用的 App
- 離線使用
- 本機儲存資料

也就是說：

最終不是把 HTML 直接拿去上架，而是根據目前 prototype 的畫面和流程，重做成真正的原生 App 或跨平台 App。

---

## 技術總方向

目前最適合這個產品的方向是：

- 跨平台 App
- 本機資料庫
- 本機圖片儲存
- 不做雲端同步
- 離線優先

你可以把整體結構想成：

`平板 App`
↓
`本機資料庫`
↓
`本機圖片與設定`
↓
`匯入 / 匯出 / 備份`

---

## 為什麼不先做雲端同步

因為這個產品的使用情境是：

- 展場
- 市集
- 攤位現場

這些地方常常會遇到：

- 網路不穩
- 手機熱點很差
- 場館 Wi-Fi 不可靠
- 現場不能等同步

如果第一版就做成很依賴雲端的架構，會有幾個風險：

- 結帳延遲
- 商品讀取慢
- 無法開單
- 匯入資料失敗
- 同步衝突

所以這個產品應該採：

**離線優先**

意思是：

- 沒網路也能正常使用
- 所有核心資料都在本機
- 雲端不是必要條件

---

## 資料要放哪裡

第一版的資料應該放在 App 裡面的本機資料庫。

最適合的方向是：

**SQLite**

你可以把 SQLite 想成：

- 放在 App 裡的一個小型資料庫
- 不需要網路
- 很適合商品、訂單、庫存、預購名單這種資料
- iOS 和 Android 都能用

它適合這個產品的原因：

- 離線穩定
- 查詢速度夠快
- 可存交易紀錄
- 好做備份
- 比單純存在瀏覽器儲存空間安全很多

---

## 圖片怎麼存

商品圖片不建議整張直接塞進資料庫欄位裡。

比較合理的做法是：

- 圖片檔案存在 App 本機儲存空間
- 資料庫只記錄：
  - 圖片檔名
  - 路徑
  - 對應哪個商品

這樣比較好維護，也比較不會讓資料庫膨脹得太快。

---

## 匯入與匯出怎麼做

### 匯入

預購名單與部分資料匯入，建議支援：

- Excel
- CSV

因為這是最符合一般使用者習慣的方式。

### 匯出

建議支援：

- 銷售紀錄匯出 CSV
- 預購名單狀態匯出 CSV
- 寄賣結算匯出 CSV
- 完整備份匯出 JSON

這樣你可以：

- 自己備份
- 用 Excel / Numbers 整理
- 換機時匯入恢復

---

## 建議的 App 技術方向

如果目標是同時做：

- iOS
- Android

而且畫面又需要很多自訂 UI，建議用跨平台框架。

目前最推薦的方向是：

### Flutter

推薦原因：

- 一套程式可同時做 iOS / Android
- 很適合平板介面
- 視覺控制力高
- 做你現在這種自訂版型和前後台流程比較穩
- 離線工具型 App 很常用這個方向

### 第二選項：React Native

也可以做，但如果是這個產品的視覺和版面需求，我目前比較傾向 Flutter。

簡單說：

如果要我幫你先定方向，我會建議：

**Flutter + SQLite**

---

## 這個組合代表什麼

如果最後採用：

**Flutter + SQLite**

意思就是：

- UI 不是延用現在 HTML 直接上架
- 而是根據現在 prototype，重新做成 Flutter 畫面
- 資料存在本機 SQLite
- 圖片存在本機
- 匯入匯出用檔案方式處理

這是很適合離線型 POS 的做法。

---

## 從現在到正式 App 的流程

### 第 1 階段：Prototype 完成

你們現在在這裡。

目標：

- 把前台 / 後台畫面與流程確認好
- 把功能優先順序整理清楚

### 第 2 階段：技術規劃

目標：

- 確定 Flutter
- 確定 SQLite
- 確定資料結構
- 確定備份與匯入匯出方式

### 第 3 階段：MVP 開發

目標：

- 真的做出可運作 App
- 接上本機資料庫
- 接上商品、庫存、預購、交易功能

### 第 4 階段：測試與上架準備

目標：

- 實機測試
- 調整效能與備份流程
- 給家人或協作者處理上架相關工作

---

## MVP 第一版該做什麼

### 必做

- 前台商品選取與結帳
- 現金付款計算機
- 商品管理
- 單一庫存管理
- 低庫存提醒
- 預購名單匯入
- 預購取件標記
- 付款方式自訂
- 匯出與備份

### 先不做

- 雲端同步
- 帳號系統
- 多人同時編輯
- 多裝置自動同步
- 複雜報表
- 進階會員功能

---

## 為什麼這條路適合你

因為你的產品不是在解決：

- 大型門市 ERP
- 餐飲點餐
- 線上商店管理

它在解決的是：

- 攤位現場快速找商品
- 離線穩定收銀
- 管理周邊、刊物、預購與寄賣

所以「小而穩」比「大而全」更重要。

這也是為什麼：

- 離線優先
- 本機資料庫
- 不急著做雲端同步

會是更對的選擇。

---

## 目前建議正式定案的技術方向

- 產品形式：平板 App
- 平台：iPad + Android 平板
- 開發方向：Flutter
- 本機資料庫：SQLite
- 圖片：本機檔案儲存
- 匯入：Excel / CSV
- 匯出：CSV / JSON
- 備份：手動匯出 / 匯入
- 同步：第一版不做
- 架構原則：離線優先

---

如果之後再有人問你：

「怎麼還在 HTML？資料庫呢？」

**「現在是在做 App 的 prototype，先確認 UI 和流程；正式技術方向會是平板 App、本機 SQLite、離線使用，資料庫會在下一階段接上。」**

這句話是合理的，也符合目前這個產品的進度。
